# GPU 제품명 파싱 정확도 재측정 (v2)

기존 50건(다나와 단일 사이트) 평가셋은 정규식 규칙을 보고 역으로 라벨링되어
정규식에 유리한 순환 편향이 있었음. 이를 제거하기 위해 평가셋을 재구성하고
정규식/LLM 파서를 다시 비교 측정함.

## 1. 평가셋 재구성

- `data/labeled_gpu_names_v2.csv` — 129건 (다나와 65 / 컴퓨존 46 / 견적왕 18)
- 라벨링 방법: `parser/regex_parser.py`를 실행하거나 참고하지 않고, 제품명 원문 텍스트만
  읽어 4개 필드(manufacturer/chipset_maker/model_name/distributor)를 사람이 직접 채움
  (`scripts/build_labeled_dataset_v2.py`).
- 의도적으로 포함한 불규칙 케이스:
  - 브랜드 약어/오타: `GALAZ`(GALAX 오타), `MANLi`(대문자 표기 `MANLI`와 불일치),
    `emTek`/`AXLE`(영문 표기, 한글 `이엠텍`/`액슬`과 동일 회사)
  - 칩셋 표기 누락: `NVIDIA 쿼드로 P2000`, `[AMD] Radeon™ PRO WX3200` — "지포스/라데온"
    토큰이 전혀 없고 브랜드명으로만 칩셋 제조사를 유추해야 하는 경우
  - 유통사 표기 혼재: `대원CTS`(축약형) vs `대원씨티에스`(정식 표기), `인텍앤컴퍼니`(정규식
    목록에 없는 신규 유통사)
  - 사이트별 포맷 차이: 컴퓨존의 `[BRAND]` 대괄호 표기, `Radeon™` 영문 트레이드마크 토큰,
    `[ZOTAC] GAMING ...`처럼 브랜드명이 분리 표기된 경우
- 정규식 파서는 새로 발견된 케이스에 맞춰 사후 수정하지 않음(수정하면 다시 순환 편향이
  생기므로, 측정 목적상 현재 구현 그대로 평가).

## 4. 원인 분석 (필드별 오류 패턴)

`scripts/debug_mismatches.py`, `debug_mismatches2.py`로 실제 불일치 사례를 확인함.

- **manufacturer / 정규식 50.4%**: 실패 원인이 거의 전부 동일 패턴 — 하드코딩된
  `MANUFACTURERS` 목록에 없는 브랜드(PowerColor, Colorful, GAINWARD, TAGER 등)와,
  컴퓨존의 `[BRAND]` 대괄호 표기를 정규식이 전혀 처리하지 못함(컴퓨존 46건 대부분 None).
  즉 "본질적으로 어려운 인식 문제"가 아니라 "목록/패턴 커버리지 문제".
- **manufacturer / LLM 88.4%**: 대괄호·신규 브랜드는 잘 처리하지만, 두 가지 약점이 보임.
  (1) 표기를 "정규화"해버림 — `emTek`→`이엠텍`, `AXLE`→`EZWIN`처럼 원문 그대로가 아니라
  LLM이 아는 정식 표기로 바꿔 답해 정확매칭에서 틀림 (의미상으론 맞지만 표기 불일치).
  (2) 낯선/오타 브랜드에서 다른 실제 브랜드명으로 환각함 — `GALAZ`(오타)를 `MSI`로,
  `TAGER`를 `NVIDIA`로 잘못 추정. 정규식은 이런 경우 None을 반환할 뿐 틀린 값을
  만들어내지는 않음.
- **chipset_maker / 정규식 91.5% vs LLM 98.4%**: 정규식의 실패는 거의 전부 의도적으로
  넣은 "칩셋 토큰 누락" 케이스(NVIDIA 쿼드로, [AMD] Radeon PRO 등)에 집중됨 — "지포스/라데온"
  사전에만 의존하기 때문에 구조적으로 못 맞음. LLM은 "NVIDIA"/"AMD"/"Quadro" 같은 맥락만
  보고도 제조사를 정확히 추론함. 이 필드가 LLM의 세계지식이 규칙 기반 대비 가장 분명하게
  우위를 보이는 지점.
- **model_name / 정규식 47.3% vs LLM 8.5%**: 두 파서 모두 낮지만 실패 양상이 다름.
  - 정규식: model_name이 "manufacturer/chipset/memory/distributor를 제거한 나머지"로
    정의되어 있어, 앞단에서 manufacturer 인식이 실패하면(대괄호, 미등록 브랜드) 그 토큰이
    그대로 model_name에 남거나, distributor 인식이 실패하면 끝에 유통사명이 붙어버림 —
    즉 다른 필드 오류가 그대로 전파되는 구조적 약점.
  - LLM: 거의 모든 오답이 "메모리 스펙(D7 16GB, D6X 12GB 등)을 떼지 않고 model_name 뒤에
    그대로 붙여서 반환"하는 동일한 포맷 습관 때문임. 칩셋/보드 변형 자체는 대부분 맞게
    추출하지만, 우리가 정한 "메모리 스펙은 model_name에서 제외" 규칙을 일관되게
    따르지 않아 정확매칭 기준으로는 거의 전부 오답 처리됨. 프롬프트에 "메모리 용량 표기는
    포함하지 말 것"을 명시하면 크게 개선될 가능성이 높음(이번 측정은 프롬프트 수정 없이
    기존 그대로 측정).
- **distributor / 정규식 91.5% vs LLM 78.3%**: 정규식은 사전에 등록된 유통사명에 한해
  꽤 안정적으로 끝부분에서 추출함. LLM은 누락률이 33.8%로 높음 — 문자열 끝에 유통사명이
  명백히 있어도(`하이퍼프로져`, `대원씨티에스` 등) 종종 `null`로 응답함. 낯선 회사명을
  "유통사"로 분류할 신호가 부족하다고 판단해 보수적으로 비워두는 경향으로 보임.

## 5. 결론 — "전체 우위"가 아니라 필드별 적합성

| 필드 | 더 적합한 방식 | 근거 |
|---|---|---|
| manufacturer | LLM (단, 환각 위험 인지 필요) | 정규식은 목록/대괄호 표기 커버리지 문제로 절반이 누락. LLM은 커버리지는 넓지만 낯선 브랜드에서 틀린 답을 "확신 있게" 만들어낼 수 있음 — 운영에 쓴다면 LLM 출력에 신뢰도 낮은 경우 None 처리하는 가드가 필요. |
| chipset_maker | LLM | 정규식은 "지포스/라데온" 토큰이 없으면 구조적으로 못 맞히는 반면, LLM은 브랜드명만으로도 추론 가능. 이번 평가의 핵심 목적("칩셋 표기 누락" 케이스)에서 가장 뚜렷한 차이. |
| model_name | 정규식 (단, manufacturer 커버리지 개선이 선행 조건) | 정규식은 manufacturer/distributor만 제대로 잘라내면 나머지가 자동으로 맞는 구조라 개선 여지가 명확함. LLM은 메모리 스펙 제거 규칙을 안 지키는 동일 패턴의 실수를 반복해 프롬프트 보강 없이는 신뢰하기 어려움. |
| distributor | 정규식 | 등록된 유통사 사전 기반 매칭이 LLM의 추론보다 안정적. LLM은 모르는 회사명을 유통사로 단정하지 않고 비워버리는 보수적 실패가 잦음(누락률 33.8%). |

전체적으로 "정규식이 좋다/LLM이 좋다"로 한 줄 결론을 내리기보다, **정규식은 사전에
등록된 패턴(유통사 목록, 지포스/라데온 토큰)에 강하고, LLM은 사전에 없는 표기 변형이나
맥락 추론(칩셋 제조사)에 강하다**는 상호보완적 특성이 뚜렷함. model_name처럼 둘 다 약한
필드는 "정규식 커버리지 보강 + LLM 프롬프트에 메모리 스펙 제외 규칙 명시"를 함께 적용하는
하이브리드가 가장 현실적인 개선 방향으로 보임(이번 작업 범위에는 포함하지 않음).
