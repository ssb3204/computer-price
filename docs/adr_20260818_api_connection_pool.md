# ADR — API 프로세스 커넥션 풀 도입과 풀 크기 결정

- **상태**: 채택 (2026-08-18)
- **관련 PR**: #23 (`feature/connection-pool`)
- **측정 원자료**: [../scripts/perf/RESULTS.md](../scripts/perf/RESULTS.md)
- **부분적으로 뒤집는 결정**: 2026-07-28 "커넥션 풀 기각" ([adr_20260728_crawl_resilience.md](adr_20260728_crawl_resilience.md)) — §6 참고

---

## 1. 맥락 — 요청 시간의 90% 가 커넥션 개설이었다

MySQL 이 Oracle Cloud VM 으로 옮겨간 뒤 API 는 요청마다 WAN 너머로 커넥션을 새로 열었다.
컨테이너 내부 실측:

| | 값 |
|---|---:|
| 순수 RTT (커넥션 재사용, `SELECT 1`) | **40.7ms** |
| connect + close (개설 비용) | **350.1ms** |
| **개설이 차지하는 비중** | **90%** |

`GET /builds` 는 쿼리 1회짜리 단순 경로인데 응답이 **419ms** 였다.
구성이 `개설 350ms + RTT 41ms + 앱 9ms` 로 정확히 맞아떨어진다.

즉 이 API 는 대부분의 시간을 **일이 아니라 연결을 만드는 데** 쓰고 있었다.

---

## 2. 결정 ① — 풀을 도입한다 (단, API 프로세스 한정)

DBUtils `PooledDB` 를 쓴다. 모듈 전역 `_pool` + `init_pool(settings, size)` 구조로,
`get_connection()` 시그니처를 유지해 호출부 30여 곳(`users_repo`/`watchlist_repo`/`build_repo`)을
고치지 않았다. CLAUDE.md 의 "새 추상화 계층(ABC/팩토리)을 만들지 않는다" 제약과 충돌하지 않는다.

**크롤러·파이프라인은 `init_pool()` 을 호출하지 않는다.** 기존 동작(매번 새 커넥션)을 유지한다.
이유는 §6.

### 효과

| | 풀 없음 | 풀 P=20 | 개선 |
|---|---:|---:|---:|
| `/builds` 단일 요청 | 419ms | **52ms** | **8.1배** |
| 처리량 천장 | 93.6 RPS | **373 RPS** | **4.0배** |
| p95 @ 동시 40명 | 455ms | **104ms** | **4.4배** |

---

## 3. 결정 ② — 풀 크기는 20

감으로 정하지 않았다. `DB_POOL_SIZE` 를 바꿔 `--force-recreate` 후 `printenv` 와
`Threads_connected` 로 **실제 적용을 확인하고** 각각 측정했다.

| P | 천장 RPS | 증가율 | 포화 동시성 | 최대 커넥션 수요 |
|---:|---:|---:|---:|---:|
| 5 | 100 | — | 8 | 5.5 = P |
| 10 | 209 | **+109%** | 15 | 11.5 = P |
| **20** | **373** | **+78%** | 30 | 20.5 = P |
| 40 | 384 | **+3%** | 60 | **21.1 ≪ P** |

동일 부하(동시 20명)에서의 p95 도 같은 지점에서 평평해진다.

| P | 5 | 10 | **20** | 40 |
|---|---:|---:|---:|---:|
| p95 | 188ms | 99ms | **82ms** | 83ms |

**처리량과 지연이 상충하지 않는다.** 보통 풀 크기는 트레이드오프 곡선을 그리는데
여기서는 P=20 에서 두 지표가 함께 평평해져 선택이 갈리지 않았다.

### 20 이라는 값이 두 계산으로 수렴한다

| 계산 | 값 |
|---|---:|
| anyio threadpool 40 × 커넥션 점유율 50% | 20 |
| CPU 천장 378 RPS × 점유시간 55ms | 21 |

두 경로가 같은 값을 주기 때문에 처음에는 어느 쪽이 지배적인지 구분되지 않았다.
어느 쪽이든 결론은 P=20 이다.

### 왜 P=40 이 무의미한가 — 병목이 풀 밖으로 나갔다

P=40 에 동시 80명을 걸어도 **커넥션 수요가 21.1 에서 멈춘다.**
`P/H = 727 RPS` 예측이 -48% 빗나간 것은 모델이 틀린 게 아니라 **풀이 더 이상
병목이 아니라는 신호**다.

```
① 커넥션 개설 350ms (요청의 90%)      → 풀 도입으로 제거 ✅
② 풀 크기 P<20                        → P=20 으로 제거 ✅
③ uvicorn 워커 1개의 GIL (~130% CPU)  ← 현재 병목
④ anyio threadpool 40                 → 도달하지 못했다. 병목이 아니었다
⑤ MySQL max_connections 151           → 한참 멀다
```

**GIL 이 병목이라는 근거**: 같은 프로세스에서 두 워크로드가 같은 CPU 천장에 멈춘다
(코어 16개 중 **1.3개**만 쓴다).

| 시나리오 | RPS | 컨테이너 CPU |
|---|---:|---:|
| `/health` (DB 없음) | 1463 | **116%** |
| `/builds` (DB 1회) | 378 | **130%** |

처리량은 4배 차이인데 CPU 는 같고 호스트는 8% 만 쓴다 → 제약이 프로세스 **안**에 있다.

### 7월 예측이 빗나간 이유

7월에는 "threadpool 이 40 이니 상한도 40" 으로 봤다. **커넥션 점유율을 100% 로 가정**했기
때문이다. 실제로 `/builds` 는 응답 52ms 중 커넥션을 쥔 시간이 **절반뿐**이고
(나머지는 HTTP·Docker 포트포워딩·직렬화), 점유율 50% 를 넣으면 상한은 20 이 된다.

→ **리틀의 법칙은 유효하다. 단 점유시간을 응답시간으로 잡으면 2배 과대추정된다.**

## 4. 결정 ③ — `mincached` 를 `size` 에서 분리한다 (기본 5)

```
mincached=5,  maxcached=20,  maxconnections=20
(DB_POOL_SIZE=20, DB_POOL_MIN_CACHED=5)
```

### 이 결정의 계기 — 있지도 않은 트레이드오프를 만들 뻔했다

처음에는 "처리량 1.8배 vs 유휴 커넥션 20개 상시 점유" 를 트레이드오프로 정리했다.
**틀렸다.** `mincached`/`maxcached`/`maxconnections` 가 전부 `size` 하나에 묶여 있어서
그렇게 보였을 뿐이다. 실측으로 셋이 서로 다른 시점을 통제함을 확인했다
(`mincached=2, maxcached=5, maxconnections=20` 으로 검증):

| 시점 | 커넥션 수 | 결정하는 파라미터 |
|---|---:|---|
| 기동 직후 | 2 | `mincached` |
| 동시 20 대여 중 | 20 | `maxconnections` |
| 전원 반납 후 | 5 | `maxcached` (초과분은 반납 시 close) |

분리하니 두 지표가 서로 싸우지 않는다:

| | `mincached=20` | `mincached=5` (채택) |
|---|---:|---:|
| 기동 대기 | **8160ms** | **2081ms** |
| 유휴 커넥션 | 20 | **5** |
| 첫 부하 최악 지연 | 405ms | **5190ms** |
| 정상 상태 처리량 | 373 RPS | **373 RPS (동일)** |

**기동을 4배 단축하면서 처리량을 그대로 유지했다.**

### `maxcached=size` 는 유지한다

낮추면(예: 5) 부하가 잦아들 때마다 초과분이 닫혀 **버스트마다 램프업을 반복**한다.
확장은 커넥션당 350ms **직렬**이라(PooledDB 가 조건 락 안에서 순차 생성, 약 2.9 커넥션/초)
`maxcached=20` 으로 두면 램프업 비용을 **1회만** 낸다.

**대가**: 재기동 후 첫 버스트의 최악 지연이 **5190ms** 다(= 15 커넥션 × 350ms).
p50 110ms · p95 130ms 는 정상이고 **최악값만** 튄다. 꼬리가 문제가 되면
`DB_POOL_MIN_CACHED` 를 올려 기동 시간과 맞바꾸면 된다.

## 5. 결정 ④ — `ping=1` 을 기각한다

DBUtils 의 `ping=1` 은 대여 시 커넥션 생존을 검사한다. 유휴 커넥션이 죽어 있는
경우(NAT/방화벽의 유휴 연결 끊김)를 막아준다.

**실측 결과 기각했다.**

| | 대여 + 쿼리 median |
|---|---:|
| `ping=0` | **50.1ms** |
| `ping=1` | **100.0ms** |
| 차이 | **+49.9ms (정확히 2배)** |

`COM_PING` 이 왕복 1회를 추가하는데, 이 환경의 RTT 가 40.7ms 라 그대로 더해진다.
**드문 실패를 막으려고 모든 요청을 2배 느리게 하는 거래**이므로 채택하지 않았다.

> 2026-07-28 기록의 "실제로 문제를 푸는 건 풀이 아니라 체크아웃 시 ping 이다" 는
> 이 실측으로 반증됐다. 비용을 재보지 않은 판단이었다.

### 대신 무엇을 할 것인가 — **미구현**

staleness 대응은 남아 있다. 검토한 두 방향:

- **예외 기반 재시도** (`OperationalError` 2006/2013 → 폐기 후 1회 재시도).
  정상 경로 비용 0. 단 커넥션은 *서버가 문장을 실행한 뒤 응답 전에도* 죽을 수 있고
  `autocommit=True` 라 재시도가 위험하다. 읽기와 파이프라인 쓰기
  (`ON DUPLICATE KEY UPDATE` 로 멱등)는 안전하지만 **API 쓰기(`create_build`, 회원가입)는
  중복 생성된다.** 읽기 한정 또는 쓰기 멱등화가 선행돼야 한다
- **유휴 수명 제한 / TCP keepalive** — 낡기 전에 갈아치우거나 NAT 가 끊지 못하게 한다.
  2026-07-28 장애가 NAT 유휴 끊김이었다면 요청당 비용 0 으로 해결된다.
  **죽은 것을 감지하는 것보다 낡지 않게 하는 쪽이 싸다.**

## 6. 2026-07-28 "커넥션 풀 기각" 과의 관계

[adr_20260728](adr_20260728_crawl_resilience.md) 은 커넥션 풀을 기각했다.
**그 판단은 여전히 유효하며, 이 ADR 이 뒤집는 것이 아니다.** 대상이 다르다.

| | 2026-07-28 | 이 ADR (2026-08-18) |
|---|---|---|
| 대상 | **크롤러 / 파이프라인** | **API 프로세스** |
| 상황 | 크롤링 5분 동안 커넥션이 유휴로 방치돼 사망 | 요청마다 커넥션을 새로 열어 350ms 낭비 |
| 문제의 성격 | 커넥션 **수명** | 커넥션 **개설 비용** |
| 결론 | 풀은 병을 키운다 → 크롤러마다 열고 닫음 | 풀이 개설 비용을 제거 → 도입 |

크롤러는 커넥션을 **거의 안 쓴다**(각 크롤러 첫머리의 `_load_watch_products()` 1회뿐)
반면 유휴 시간이 길다. 풀이 줄여줄 비용이 애초에 없고, 유휴 사망 위험만 커진다.
API 는 정반대다 — 짧은 요청이 빈번하고 유휴가 짧다.

**그래서 `init_pool()` 을 API 진입점(`main.py` 의 lifespan)에서만 호출한다.**
같은 `get_connection()` 을 쓰지만 풀이 없으면 매번 새 커넥션을 여는 구조라
파이프라인 코드는 한 줄도 바뀌지 않았다.

## 7. 트레이드오프 정리

### 얻은 것
- 단일 요청 8.1배, 처리량 4.0배, p95 4.4배
- 기동 대기 8160ms → 2081ms (`mincached` 분리)

### 대가
| | 내용 |
|---|---|
| 유휴 커넥션 5개 상시 | 부하 후에는 20개가 유지된다(`maxcached=20`) |
| 재기동 후 첫 버스트 최악 5190ms | p50·p95 는 정상. 최악값만 튄다. 1회성 |
| staleness 미구현 | `ping=0` 이라 죽은 커넥션을 대여할 수 있다. §5 |
| 워커 확장 시 제약 이동 | 워커마다 `init_pool()` 이 돌아 총 커넥션이 `워커 × 20`. 워커 7개 부근에서 MySQL `max_connections=151` 이 **처음으로** 실제 제약이 된다 |

### 이 결론의 한계
- **엔드포인트 1개(`/builds`)에서만 측정했다.** 점유율 50% 는 이 경로의 값이다.
  `price-trend`(점유시간 3배)는 점유율 73% 로 **추정**되어 최적 P 가 29 부근일 수 있다 — 미측정
- 목표 RPS·p95 를 정하지 않았다. **P=20 결론은 목표와 무관하게 성립한다**(20 을 넘으면
  어떤 지표도 변하지 않으므로). 다만 이는 곡선이 평평해진 덕이고, 완만하게 계속 올랐다면
  목표 없이는 최적점을 고를 수 없었다

## 8. 재현 시 반드시

```bash
# 컨테이너 env 는 생성 시점에 굳는다. restart 로는 안 바뀐다
DB_POOL_SIZE=<P> DB_POOL_MIN_CACHED=<P> docker compose up -d --force-recreate api
docker compose exec -T api printenv DB_POOL_SIZE          # 실제 적용 확인 필수
```

이걸 몰랐다면 P 를 5/10/20/40 으로 바꿔도 **전부 20 에서 측정돼** 네 곡선이 같게 나왔고,
**"풀 크기는 성능에 무관"** 이라는 정반대 결론이 나왔을 것이다. 실제로 한 번 그렇게 됐다.

스윕 시에는 `mincached = maxconnections` 로 맞춘다. `mincached < maxconnections` 이면
부하 중에 풀이 자라고 확장이 350ms 직렬이라 초기 계단이 **부분 워밍 상태로 측정된다**
(실측: 373 → 325 RPS).

파라미터 분리 동작과 ping 비용은 이 스크립트로 재현한다:

```bash
docker compose exec -T api python - < scripts/perf/verify_pool_params.py
```
