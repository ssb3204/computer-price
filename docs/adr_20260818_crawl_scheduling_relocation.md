## 1. 맥락 — 무엇이 강제했나

두 가지가 겹쳤다. 하나는 우리가 만든 제약이고, 하나는 원래 있었는데 안 보이던 문제다.

### 1-1. OCI 3306 을 좁히면서 러너가 접속 불가가 됐다

MySQL 은 Oracle Cloud VM 에 있고 GitHub 러너가 **인터넷을 통해** 붙는 구조였다.
그러려면 Security List 인바운드가 `0.0.0.0/0` 이어야 했다.

2026-08-17 커넥션 풀 작업 중 측정 문서에 VM 호스트 IP 가 공개 저장소로 올라간 것이
발견됐고, 그 대응으로 3306 허용 대역을 가정용 회선 `/32` 로 좁혔다.
**그 순간 러너는 MySQL 에 붙을 수 없게 됐다.**

### 1-2. 컴퓨존은 원래부터 러너 IP 에서 막혀 있었다

이관과 무관하게, 점검 중 발견했다.

| 회차(UTC) | 다나와 | 컴퓨존 | 견적왕 |
|---|---:|---:|---:|
| 08-18 06:48 | 1 | **0** | 3 |
| 08-18 02:16 | 1 | 3 | 3 |
| 08-17 20:30 | 2 | **0** | 3 |
| 08-17 15:27 | 2 | **0** | 3 |
| 08-17 07:01 | 2 | **0** | 3 |

**4회 중 3회가 0건인데 워크플로우는 전부 `success` 로 끝났다.** 크롤러가 대상 미발견을
warning 으로만 남기고 파이프라인은 나머지를 정상 처리하기 때문이다.
[adr_20260728](adr_20260728_crawl_resilience.md) 이 "간헐적 차단" 으로 기록해둔 것이
그 사이 상시에 가까워져 있었다.

## 2. 실측 — 사이트마다 차단하는 대역이 다르다

**같은 코드·같은 헤더로 출발지만 바꿔** 측정했다. 코드 변경 없이 IP 만 달라진 비교다.

| 출발지 | 다나와 | 컴퓨존 | 견적왕 |
|---|:---:|:---:|:---:|
| GitHub Actions 러너 (Azure) | 부분(2중 1~2) | **0건** | 3/3 정상 |
| Oracle Cloud VM | **불안정** | **3건 정상** | **403 Forbidden** |
| 가정용 회선 | 정상 | — | 200 정상 |

근거:

- **컴퓨존** — VM 에서 3건 수집. 러너에서 0건이던 것과 같은 코드다
- **견적왕** — 토큰 요청(`product_search.html`)부터 403. 가정용 회선에서 같은 요청은
  200 이고 응답에 `search_query` 토큰이 포함된다. 헤더·바디가 동일하므로 출발지 IP 문제다.
  VM 공인 IP 를 재할당해 재시도했으나 같은 대역(`161.33.0.0/16`)이 배정돼 결과 동일
- **다나와** — VM 에서 `9070` 이 2초 만에 미발견. 같은 시각 가정용 회선에서
  `search_products('9070')` 은 30건을 반환하고 대상 pcode 가 **두 번째**로 나온다

### 이 실측이 뒤집은 통념

`scripts/diagnose_compuzone.py` 는 로컬에서 항상 통과한다. 0건의 원인이 셀렉터나 요청
계약이 아니라 **출발지 IP** 이기 때문이다. 진단 도구가 재현하지 못하는 종류의 실패다.

→ **0건을 보면 셀렉터·파서보다 출발지 IP 를 먼저 의심해야 한다.**

## 3. 검토한 대안과 기각 사유

### A. GitHub 러너 IP 대역을 Security List 에 허용

`api.github.com/meta` 의 `actions` 대역을 인바운드에 등록한다.

**기각.** 대역이 수천 개 CIDR 이고 수시로 바뀐다. OCI Security List 는 규칙 수 상한이
훨씬 낮아 애초에 들어가지 않는다. 자동 갱신을 만들어도 상한 문제는 남는다.

### B. VM 에 self-hosted 러너 설치

워크플로우·실행 이력을 그대로 유지하면서 MySQL 을 `localhost` 로 붙는다.

**기각 — 자원 부족.** VM 실측:

```
Mem:   956Mi total / available 422Mi
Swap:  2.0Gi 중 333Mi 이미 사용 중     ← MySQL 만으로 이미 물리 메모리 부족
nproc: 2
```

러너는 상주 프로세스다(.NET 에이전트, 유휴에도 150~300MB + GitHub 롱폴링).
스왑을 이미 쓰고 있는 상태에 얹으면 OOM 위험이 실재한다.
A1.Flex(ARM, 최대 24GB)로 옮기면 가능하지만 인스턴스 교체 비용이 이 결정의 범위를 넘는다.

### C. `0.0.0.0/0` 복원

**기각.** 1-1 의 원인을 되돌리는 것이다. 게다가 컴퓨존 차단(1-2)은 그대로 남아
문제의 절반만 되돌리는 셈이다.

### D. 견적왕만 프록시 경유

**보류.** 비용과 관리 포인트가 늘고, 이 시점에는 견적왕이 막힌다는 사실 자체를
방금 알아낸 참이라 판단 근거가 부족했다.

## 4. 결정

**크롤링을 Oracle Cloud VM 의 cron 으로 옮기고 `.github/workflows/crawl.yml` 을 삭제한다.**
GitHub Actions 는 CI 전용이 된다.

```
0 1,6,15,20 * * * cd /home/ubuntu/price-pipeline && .venv/bin/python run_pipeline.py >> /home/ubuntu/crawl.log 2>&1
```

| 항목 | 값 |
|---|---|
| 코드 | `~/price-pipeline` (리포 clone) |
| Python | 3.11 (deadsnakes PPA) + venv |
| MySQL | `127.0.0.1:3306` |
| 시간대 | `Etc/UTC` → UTC 시각이 곧 KST 10/15/00/05시 |
| 로그 | `~/crawl.log` |

### `cd` 가 필수인 이유

`src/common/config.py` 의 `env_file=".env"` 가 **상대경로**다. cron 은 홈 디렉토리에서
실행되므로 `cd` 없이는 `.env` 를 못 찾고 `MySQLSettings` 의 기본값(`localhost`)으로
**조용히** 떨어진다. 에러가 아니라 다른 곳에 붙으려다 실패하므로 원인 추적이 어렵다.

`env -i` 로 빈 환경을 재현해 `cd` + venv 조합이 `.env` 를 읽는 것을 확인했다.

## 5. 트레이드오프

### 얻은 것

| | 근거 |
|---|---|
| **컴퓨존 수집 복구** | 0건 → 3건. 러너에서 4회 중 3회 0건이던 문제가 해소됐다 |
| **3306 외부 개방 불필요** | 파이프라인이 `127.0.0.1` 로 붙는다. 공개 저장소 IP 노출 문제의 근원이 사라진다 |
| **커넥션 개설 비용 소멸** | WAN 경유 350ms → 같은 호스트 수 ms. [RESULTS.md](../scripts/perf/RESULTS.md) 기준 요청 시간의 90% 를 차지하던 항목이다 |
| **GitHub Secrets 불필요** | MySQL 접속 정보 5개를 삭제했다. 자격증명 보관처가 하나 줄었다 |

### 잃은 것

| | 영향 |
|---|---|
| **Actions UI 실행 이력·로그** | 웹에서 회차별 성패를 훑어볼 수단이 없다. `~/crawl.log` 가 유일한 단서다 |
| **견적왕 수집 (3건)** | Oracle 대역 403. 러너에서는 3/3 정상이던 것이다 |
| **다나와 안정성** | VM 에서 불안정. 데이터 2점이라 확정은 아니나 러너보다 나쁘다 |
| **VM 가용성에 종속** | 러너는 GitHub 이 관리했다. 이제 VM 이 죽으면 크롤링도 죽는다 |

### 정면으로 인정할 것 — 이 결정은 총 수집량을 늘리지 않았다

```
이관 전 (러너)  : 다나와 1~2 + 컴퓨존 0 + 견적왕 3 = 4~5건 / 9건
이관 후 (VM)    : 다나와 0   + 컴퓨존 3 + 견적왕 0 = 3건   / 9건
```

**어느 한 곳에서도 3사를 모두 수집할 수 없다.** 이관의 정당성은 수집량이 아니라
1-1(러너가 MySQL 에 붙을 수 없다)에 있다. 그 제약 아래에서 가능한 선택지 중
자원·비용 조건을 만족하는 것이 VM cron 이었다.

수집량 회복은 별도 과제다(§7).

## 6. 부수 결정 — 견적왕 크롤러를 그대로 둔다

403 이 확정됐지만 크롤러를 제거하지도, 워치리스트를 비활성화하지도 않는다.

| 방안 | 판단 |
|---|---|
| **그대로 두기** ✅ | 파이프라인이 막히지 않는다 — `실패: 1개 사이트` 로 기록하고 나머지를 정상 적재하는 것을 실측했다. 차단이 풀리면 **코드 수정 없이** 복구된다 |
| `stg_watchlist.is_active=0` | **위험.** 해당 상품이 공개 조합(`build_items`)에 담겼으면 남의 화면에서 가격 추이가 멈춘다. CLAUDE.md 에 기록된 함정이다 |
| 크롤러 코드 제거 | 되살릴 때 PR 이 또 필요하고, 되살려야 한다는 사실 자체를 잊기 쉽다 |

**비용**: 회차마다 403 요청 3회(수 초)와 로그 3줄이 쌓인다. 그리고
`실패: 1개 사이트` 가 **상시 상태**가 되어, 다나와·컴퓨존이 진짜로 죽어도 묻힌다.
감시를 붙일 때 "견적왕 외의 실패만 알림" 조건이 필요하다.

## 7. 남은 위험 — 실패가 어디에서도 보이지 않는다

이번 점검에서 드러난 가장 큰 문제이며, 이관과 무관하게 존재한다.

컴퓨존 `SK hynix Gold P31` 은 **2026-08-07 이후 11일간 수집이 없었다.**
그런데 세 곳 모두에서 정상으로 보였다:

| 관측 지점 | 왜 안 보였나 |
|---|---|
| 파이프라인 로그 | `대상 미발견` warning 만 남고 exit code 는 0 |
| quality 검증 | `손실률 0.0%` **통과** — 수집된 것만 검사하므로 애초에 안 들어온 건 대상이 아니다 |
| 웹 차트 | **forward fill** 이 빈 날을 직전 가격으로 메운다. "일시적 실패로 선이 끊기지 않게" 하려던 규칙이 **장기 실패도 똑같이 가린다** |

이관 후에는 Actions UI 마저 없으므로 상황이 나빠졌다.

### 후속 과제

1. **감시 수단** — 현재 0. `SLACK_WEBHOOK_URL` 을 VM `.env` 에 넣지 않아 알림 단계를
   건너뛴다. 붙일 때 "견적왕 외의 실패만" 조건이 필요하다(§6)
2. **최종 수집 시각 노출** — 워치리스트 화면에 상품별 마지막 수집 시각을 보여주면
   forward fill 이 가리는 정체를 즉시 알 수 있다. 차트만으로는 불가능하다
3. **짧은 검색어** — `sk`(2자)가 다나와·컴퓨존 양쪽에서 간헐 실패한다. 결과가 수천 건이라
   대상이 스캔 범위를 들락거린다. 성공하는 검색어는 전부 모델명·브랜드
   (`9800` `7800` `9070` `5070` `SAPPHIRE` `adata` `라이젠`). 등록 시 최소 글자수 검증을
   걸지 검토한다
4. **다나와 VM 불안정** — 데이터 2점. 회차를 더 관찰해 확정한다
5. **견적왕 복구 경로** — 프록시(§3-D) 또는 가정용 회선 활용. 집 IP 는 이미 3306 허용
   목록에 있고 견적왕이 200 이라 기술적으로는 가능하나, PC 상시 가동이 전제다
