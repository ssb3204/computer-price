## 1단계 — `/health` 대조군 (2026-08-17)

DB 를 타지 않는 경로. 여기서 나온 RPS 가 이후 모든 수치의 해석 기준이다.
커넥션 풀과 무관하므로 브랜치 왕복 없이 1회만 측정.

### 계단식 (단일 프로세스, 각 30초)

| 동시 사용자 | RPS(평균) | p50 | p95 | p99 | 실패 |
|---:|---:|---:|---:|---:|---:|
| 1 | 835.7 | 1.0 | 1.0 | 2.0 | 0 |
| 5 | 1373.5 | 1.8 | 4.0 | 4.9 | 0 |
| 10 | 1649.7 | 3.1 | 6.5 | 7.6 | 0 |
| 20 | 1742.1 | 4.6 | 11.6 | 14.0 | 0 |
| 40 | 1781.0 | 6.0 | 21.7 | 25.9 | 0 |
| 80 | 1792.2 | 9.1 | 40.9 | 49.3 | 0 |
| 160 | 1790.0 | 11.6 | 77.8 | 95.1 | 0 |

RPS 는 20 사용자부터 평평(1742 → 1790, +2.8%)한데 p95 는 선형 상승(11.6 → 77.8).
**교과서적 포화 패턴** — 포화 후 동시성 추가는 처리량이 아니라 큐 대기만 늘린다.
포화 시작점 ≈ 동시 **10~20**.

### 천장 귀속 확인 (master + worker 4, 160 사용자 60초)

| 방식 | RPS | p50 | p95 | max |
|---|---:|---:|---:|---:|
| 단일 프로세스 | 1790.0 | 11.6 | 77.8 | — |
| master+worker 4 | **1787.1** | **89** | **100** | 210 |

- **RPS 가 동일 → 천장 1790 은 Locust 가 아니라 API 측.** 부하 생성기는 결백하다.
- 리틀의 법칙 정확히 성립: `160 ÷ 1787 = 89.5ms` = 실측 p50 89ms.
- **단일 프로세스는 지연을 과소보고한다** (p50 11.6 vs 89, p95 77.8 vs 100).
  그린렛이 CPU 를 기다리는 시간이 응답시간에 안 잡히기 때문.
  → **RPS 는 단일 프로세스로도 되지만, 지연 수치는 반드시 분산 모드로 잰다.**

### 결론

```
환경 천장 ≈ 1790 RPS  (uvicorn 1 워커 + Docker Desktop 포트포워딩 + 앱 CPU)
```

예측된 `/builds` 수치와 비교하면 헤드룸이 충분하다:

| | 예측 RPS | 천장 대비 |
|---|---:|---:|
| 풀 없음 (`40 / 0.2923s`) | 137 | 7.7% |
| 풀 P=10 (`10 / 0.0496s`) | 200 | 11% |
| 풀 P=40 | 806 | 45% |

→ **측정 환경이 DB 병목을 가리지 않는다.** 2단계 진행 가능.
(P=40 예측치 806 은 천장의 45% 라 여유가 줄어든다 — 그 구간 해석 시 주의)

### 원인 ① — 컨테이너 env 가 생성 시점에 굳어 있었다 (핵심)

```
Created:   2026-07-31T09:38:34Z   ← DB_POOL_SIZE=20 이 이때 박혔다
StartedAt: 2026-08-17T06:59:53Z   ← 오늘은 start 만 됐다
printenv DB_POOL_SIZE → 20
부하 중 MySQL Threads_connected → 20 (40초간 고정, 유휴 시에도 20)
```

**오늘 측정 전부가 P=10 이 아니라 P=20 에서 이뤄졌다.** `docker compose up -d` 는 이미 있는
컨테이너를 재사용하므로 `docker-compose.yml` 의 기본값 10 이 적용되지 않았다.

> **스윕 절차에 반드시 넣을 것**
> ```
> DB_POOL_SIZE=<P> docker compose up -d --force-recreate api
> docker compose exec -T api printenv DB_POOL_SIZE      # 반드시 확인
> curl --retry 15 --retry-delay 1 --retry-connrefused .../health
> SHOW STATUS LIKE 'Threads_connected'  → P 와 일치하는지 확인
> ```
> `restart` 로는 env 가 갱신되지 않는다. 이걸 몰랐다면 P 를 5/10/20/40 으로 바꿔도
> 전부 20 에서 측정돼 네 곡선이 같게 나왔고, **"풀 크기는 성능에 무관"** 이라는
> 정반대 결론이 나왔을 것이다.
>
> `mincached=P` 라 기동 시 커넥션을 미리 다 연다(개당 350ms). P=10 이면 약 3.5초간
> 요청을 받지 않는다 — 재생성 직후 `/health` 가 http 000 으로 실패하는 것을 확인했다.
> 스윕 스크립트에 기동 완료 폴링이 없으면 첫 계단이 통째로 실패한다.

### 원인 ② — 커넥션 점유율을 100% 로 잡은 게 틀렸다

DBUtils 는 결백하다. 통제 실험(컨테이너 내부, DBUtils 3.1.2):
`maxconnections=3` 풀에 12스레드가 동시에 대여를 시도 → 커넥션 **3개 유지**. 정상 동작.

P=20 으로 역산하면 모델이 맞는다:

```
점유시간 = 20 커넥션 ÷ 364 RPS = 55ms
점유율   = 55ms ÷ 109ms(40명 평균응답) ≈ 50%
```

| | 애초 가정 | 실측 교정 |
|---|---|---|
| 풀 크기 | 10 | **20** |
| 커넥션 점유시간 | 52ms (= 응답 전체) | **55ms** |
| 점유율 | ≈100% | **≈50%** |
| 포화 동시성 | P 명 | **2P 명** |
| 최대 RPS | P × 19 | **P × 18.2** |

응답의 절반은 커넥션 밖(HTTP·Docker 포트포워딩·직렬화·threadpool)에서 쓴다.
그래서 꺾임이 P 명이 아니라 **2P 명**에서 일어난다 — 40명까지 RPS 가 계속 오른 이유다.

참고 실측(컨테이너 내부, 커넥션 1개 재사용):

| | median |
|---|---:|
| 순수 RTT (`SELECT 1`) | **40.7ms** |
| connect+close (개설비용) | **350.1ms** |

7월 기록(RTT 49.6 / 개설 292.3, 호스트 측정)과 다르다. 개설비용이 커진 것은 Docker 경유와
네트워크 변동 탓으로 보인다. **`mysql_client.py:57` 의 `ping=0` 주석 "RTT 41ms" 는
오늘 실측 40.7ms 와 사실상 일치한다** — 7월에 남긴 "주석이 틀렸다"는 판단은 취소한다.

### 부산물: P=20 데이터 확보

위 표는 버리는 데이터가 아니라 **스윕의 P=20 지점**이다(`out/s1_P20_*.csv`).
P=20 에서 처리량 천장 ≈ **364~373 RPS**, 꺾임 ≈ 동시 40명.



## 5단계 — 풀 크기 스윕 (2026-08-17, `--tags s1`)

각 P 마다 `DB_POOL_SIZE=<P> docker compose up -d --force-recreate api` 후
`printenv` + `Threads_connected` 로 **실제 적용을 확인하고** 측정했다(전부 기대값 일치).

| P | 천장 RPS | 증가율 | 포화 동시성 | 실효 점유시간 `P/천장` | 최대 커넥션 수요 |
|---:|---:|---:|---:|---:|---:|
| 5 | 100 | — | 8 | 50.0ms | 5.5 = P |
| 10 | 209 | **+109%** | 15 | 47.8ms | 11.5 = P |
| 20 | **373** | **+78%** | 30 | 53.6ms | 20.5 = P |
| 40 | 384 | **+3%** | 60 | — | **21.1 ≪ P** |

### 결론: 최적 풀 크기 = **20**

곡선이 P=20 에서 평평해진다. P=40 은 커넥션을 2배 쓰고 처리량은 +3%(변동 범위 안)다.

동일 부하(동시 20명)에서의 p95 도 같은 지점에서 평평해진다 — 처리량과 지연이 상충하지 않는다.

| P | p95 @ 20명 |
|---:|---:|
| 5 | 188ms |
| 10 | 99ms |
| 20 | **82ms** |
| 40 | 83ms |

### 왜 20 인가 — 병목이 풀에서 threadpool 로 이동했다

```
anyio threadpool 토큰            = 40      (동시 실행 핸들러 상한)
커넥션 점유율                    ≈ 50%     (응답의 절반은 HTTP·Docker·직렬화)
→ 동시 커넥션 수요 상한          = 40 × 0.5 ≈ 20
```

실측이 그대로 재현한다: P=40 을 주고 동시 80명을 걸어도 커넥션 수요가 **21.1** 에서 멈춘다.
`P/H = 727 RPS` 예측이 -48% 빗나간 것은 모델이 틀린 게 아니라 **풀이 더 이상 병목이
아니라는 신호**다.

7월 예측("threadpool 40 이니 P>40 은 무의미")은 점유율 100% 가정 때문에 상한을 2배로
잡았다. 실측 점유율 50% 를 넣으면 **상한은 20** 이다.

**이 결론은 목표 RPS·p95 를 정하지 않아도 성립한다** — 20 을 넘으면 어떤 지표도 변하지 않는다.
반대로 커넥션을 아끼는 것이 목표라면 P 를 낮춰 처리량을 사는 트레이드오프가 가능하다
(P=10 이면 커넥션 절반으로 처리량 56%).

### 부수 발견 — 기동 대기에 `--retry-all-errors` 가 필요하다

`--retry-connrefused` 로는 부족하다. Docker 포트 프록시가 연결은 수락하고 앱이 아직
안 떠서 **빈 응답(curl exit 52)** 이 오는데, 이건 connection-refused 가 아니라 재시도되지
않는다. P=40 은 기동에 `40 × 350ms ≈ 14초` 가 걸린다.

```bash
curl -s --retry 40 --retry-delay 1 --retry-all-errors http://localhost:8001/health
```

## 4단계 — before / after 종합

| | 풀 없음 (`master`) | 풀 P=20 | 개선 |
|---|---:|---:|---:|
| `/builds` 단일 요청 | 419ms | **52ms** | **8.1배** |
| 처리량 천장 | 93.6 RPS | **373 RPS** | **4.0배** |
| p95 @ 동시 40명 | 455ms | **104ms** | **4.4배** |
| 유휴 커넥션 | 0 | 20 (상시) | — |
| 병목 | 커넥션 개설 350ms | uvicorn 워커 1개의 GIL | **이동 완료** |

### 병목 계층 (측정으로 확정된 순서)

```
① 커넥션 개설 350ms (요청의 90%)      → 풀 도입으로 제거 ✅
② 풀 크기 P<20                        → P=20 으로 제거 ✅
③ uvicorn 워커 1개의 GIL (~130% CPU)  ← 현재 병목
④ anyio threadpool 40                 → 도달하지 못함. 병목이 아니었다
⑤ MySQL max_connections 151           → 한참 멀다
```

### GIL 이 병목이라는 근거

같은 프로세스에서 두 워크로드가 **같은 CPU 천장**에 멈춘다(코어 16개 중 1.3개만 사용):

| 시나리오 | 동시 | RPS | 컨테이너 CPU | CPU/요청 |
|---|---:|---:|---:|---:|
| `/health` (DB 없음) | 40 | 1463 | **116%** | 0.79ms |
| `/builds` (DB 1회) | 40 | 378 | **130%** | 3.44ms |

처리량은 4배 차이인데 CPU 는 같다. 호스트는 8% 만 쓰므로 제약은 프로세스 **안**에 있다.
→ **threadpool T 를 늘려도 처리량은 오르지 않는다.** 다음 레버는 스레드가 아니라
**uvicorn 워커 수**(프로세스마다 GIL 이 따로)다. 단 워커마다 `init_pool()` 이 돌아
총 커넥션이 `워커 × P` 가 되므로 그때 MySQL 151 이 처음으로 실제 제약이 된다.

### P=20 의 근거는 두 갈래로 수렴한다

| 계산 | 값 |
|---|---:|
| threadpool 40 × 점유율 50% | 20 |
| CPU 천장 378 RPS × 점유시간 55ms | 21 |

두 경로가 같은 값을 주기 때문에 앞서 구분되지 않았다. 어느 쪽이든 **P=20**.
